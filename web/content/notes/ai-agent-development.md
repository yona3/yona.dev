Codex や Claude Code に作業を任せながらコードを書く時間が、ここ最近で一番長い。最初は「速く書いてもらえる」ことを期待していたが、実際に変わったのは判断の粒度のほうだった。

agent に渡すために、頭の中にしかなかった意図を文章で書き起こす。返ってきた変更を読んで、受け取るか書き直してもらうかを決める。レビューに二人目が常にいる前提で進めることで、自分が何を考えていたのかが残りやすくなった。

## 任せる前に書くこと

agent に渡せる入力の質が、そのまま結果の質を決める。曖昧な依頼は曖昧な結果を返してくるし、抽象的すぎる依頼はもっともらしい嘘になりやすい。

依頼する前に、最低限これだけは書くようにしている。

- 何を変えたいのか (UI / 振る舞い / 内部構造のどれか)
- どこを変えてよく、どこは触らないでほしいか
- 完了の判断基準 (テストが通る、画面で確認した、など)
- 失敗したら何に戻ればよいか

これは agent に渡すためというより、自分が何を頼みたいのかを確認する作業に近い。書いている途中で「これは自分で決めたほうが早い」と分かることも多い。

```md
## 目的
note 詳細ページの見出しまわりの余白を広げたい。
## 触ってよい範囲
web/src/components/site/site.module.css の `.markdown` 系のみ。
## 完了条件
h2 の前後余白が十分に広がっており、ブラウザで確認した。
```

仕様の draft はこれくらい短くてよい。長く書きすぎると、書くこと自体が目的化する。

## 受け取るときの読み方

agent から返ってくる diff を、最初の頃は流し読みしていた。今はゆっくり読む時間を確保するようにしている。

### 三回読む

一度目は意図通りかを確認する。二度目は副作用や周辺への影響を確認する。三度目は、自分ならこう書かないだろうという違和感を探す。違和感の正体が「好み」なら受け入れて、「設計」なら書き直してもらう。

### 採否を曖昧にしない

「だいたいよさそう」で merge すると、後から判断の根拠が消える。受け取るか、書き直してもらうか、自分で書き直すかを毎回決めるようにしている。

## このサイトでの実験

任せる側と決める側を分けながら作業すると、コードと同じくらい言葉を書く時間が増える。書き留めておく場所が必要になり、このサイトもその実験の一部として育てている。
